# TetraFree 3.1.4 — агент, автоматизации и отмена

> Результаты и ограничения проверки приведены в разделе ниже; audit не означает применение исправлений.

Дата: 2026-10-13. Этот раздел доведен главным аудитором после прерывания агентной сессии. Код проекта не изменялся. Результаты первоначального harness сверены с исходниками. **Нельзя называть весь первоначальный прогон зеленым: 17 проверок, 16 pass, 1 fail.** Ошибка была в первой версии проверки autoVerify (ожидался успех команды, проверка файла закономерно завершалась ошибкой); отдельная корректная проверка эффекта в том же прогоне прошла. Итогового повторного прогона всего набора до сброса среды не было.

Репродукции исполняли настоящие engine/Turn/autorun/backend функции через bundle с контролируемыми store, provider, API и transports. Это не production Windows/model E2E. Первичные файлы harness утрачены при сбросе среды; stdout восстановлен из event84 дочерней сессии. Дополнительно исходники проверены главным аудитором после сброса. Рабочие shell-injection payloads/цепочки в этот отчет не включены.

P1 — существенная потеря данных, неверное выполнение или нарушение ожидаемой отмены/уровня агентного запуска. P2 — ограниченный сценарий, протокольный/защитный риск или поведение с дополнительными условиями. Отдельные связанные симптомы объединяются в итоговом backlog.

## Находки

### A01 · P2 — dangerOf не является надежной границей подтверждения

`src/agent/danger.ts:75–120`; `src/agent/engine.ts` runCommand.

Удаление quoted-частей и поверхностное выделение executable/subcommand не учитывают полную семантику shell, команды-обертки и параметры до subcommand. Harness показал пропуск опасного эффекта на искусственном Linux sentinel. **Это не подтверждение всех таких форм на Windows**; сама эвристическая природа уже известна в документации. Не считать очередную эвристику полноценной песочницей.

Защита: структурированный allowlist команд для ограниченного режима, явное разрешение любой неразобранной формы; выполнение проекта в OS-песочнице с ограничениями и минимумом env.

### A02 · P1 — старый завершающийся ход удаляет controller нового хода

`src/agent/engine.ts:329–331,419–422`.

runTurn прерывает старый controller и устанавливает новый; finally старого без проверки identity удаляет controllers[chatId] и снимает running. Harness: запустить два хода, завершить прерванный первый — isRunning false при живом втором, Stop не abort второй.

Исправление: generation/controller identity перед каждой cleanup-мутацией; scoped cleanup сообщений, lanes и running.

### A03 · P1 — после Stop исполняются следующие действия текущего ответа

`src/agent/engine.ts:598–601,621–677`.

В цикле actions отсутствует guard перед dispatch. MCP/web проверяют abort **после** await; shell проходит без общей precheck. Stop во время первой команды не предотвращает dispatch следующей shell/MCP. Harness подтвердил вызов второго exec с aborted=true и следующий MCP call.

Исправление: precheck перед каждым эффектом и после await; cancellation token во всех tool-клиентах. Связано с A04, но исправление только клиента shell не остановит MCP.

### A04 · P1 — bExec запускает команду с уже отмененным signal

`src/lib/backend.ts:198–244`, особенно `onAbort`/fetch.

Listener добавляется к уже aborted сигналу (событие повторно не приходит); signal в fetch не передается, precheck отсутствует. Реальная функция при aborted signal всё равно отправила POST /api/exec в mock fetch. Возможен dispatch команды после Stop.

Исправление: reject до POST при aborted; cancel transport/run lifecycle без гонки между launch и kill, учитывая server acknowledgment.

### A05 · P1 — автоматизация отправляет модели пустую задачу вместо одобренного prompt

`src/agent/autorun.ts:124–126`; `src/agent/engine.ts:233–245,307–315`.

fireAuto передает agent-текст как text, extra='', opts.silent задан. sendMessage для silent использует **extra как prompt**, text игнорирует. Harness: одобренная инструкция отсутствует в wire messages, последний user.content=''. Запуск расходует токены без утвержденной задачи.

Исправление: разделить пользовательский prompt и служебную строку отображения в API; не перегружать silent семантикой loop extra.

### A06 · P1 — одобренный tier автоматизации не применяется к существующему одноимённому чату

`src/agent/autorun.ts:110–126`; выбор agent/tier в `src/agent/engine.ts:270–311`.

Поиск чата только по title. Tier задается лишь при createChat; уже существующий Builder может быть «Уведомить», несмотря на одобренную «Эскалацию». Harness: файл автоматически записан без карточки подтверждения при approved tier=Эскалация.

Исправление: запускать с явно утвержденными pid/agent/tier, идентифицировать automation chat по automation ID, не названию; проверять эффективную политику после approval.

### A07 · P1 — смена проекта во время проверки approval перенаправляет задачу

`src/agent/autorun.ts:77–85,99–105`.

projectId проверяется до await autoHash, но saveTask/createChat выбирают текущий проект после await. Harness: fireAuto для A, переключение на B до digest, задача создана в B.

Исправление: явный pid всем actions и revalidation lifecycle после await; не менять адресата на текущий проект.

### A08 · P1 — live write молча затирает человеческую правку, сделанную во время стрима

`src/agent/turn.ts:108–111,142–166`.

before снимается при begin, endWrite без compare/merge пишет final content. Harness: begin на BEFORE, human work в store во время стрима, endWrite заменяет его агентным результатом без confirm.

Исправление: expected revision/three-way merge непосредственно перед commit; сохранять конфликтные версии. Защита только applyProposed этого пути не охватывает.

### A09 · P1 — принятие устаревших delete/rename не защищает новые данные

`src/agent/engine.ts:95–102,120–133`.

Stale-check исключает delete/rename. Пока карточка ждет решения, назначение rename может быть занято новым файлом, а delete-файл может получить новые правки. Harness: accept rename затирает новое destination; accept delete удаляет новое содержимое без предупреждения.

Исправление: сравнить оба конца rename и поколение всех файлов delete непосредственно при accept, including folder operations; подтверждение исходной карточки не равно разрешению на уничтожение появившихся позже данных.

### A10 · P1 — откат удаления/переименования не проверяет последующие правки

`src/agent/engine.ts:164–203`.

changed исключает delete/rename. Восстановление удаленного файла перезаписывает новый файл пользователя в том же пути. Harness подтвердил замену new human на old без confirm. Rename имеет аналогичную незащищенную ветку, отдельно нативно не проверялся.

Исправление: expected generation обоих путей, compare-before-revert, сохранение recovery-copy; не пропускать операции только потому, что они не edit.

### A11 · P2 — syncSegs не учитывает отмену при применении закрытых операций

`src/agent/engine.ts:576–601,853–944`.

Финальный/interval pump применяет file-операции без T.aborted guard. Harness вызвал реальный syncSegs на aborted Turn и подтвердил применение delete. **Это компонентная проверка функции, не доказанный полный сценарий конкретного provider abort**: обычная ошибка streamChat может выйти до финального pump. Но поздний callback/ответ не должен мутировать данные после отмены.

Исправление: guard на входе и перед каждой мутацией, generation stream callbacks; определить политику сохранения уже завершенных до Stop правок отдельно от новых.

### A12 · P2, platform-dependent — autoVerify строит shell-строку из имени файла

`src/agent/engine.ts:684–699`.

Выбранный путь встраивается в quoted shell command вместо отдельного argv. Harness на Linux подтвердил shell-интерпретацию синтаксиса допустимого имени до проверки файла. Продукт Windows-only: **тот же эффект через cmd не подтвержден**, точные cmd quoting/expansion требуют отдельной проверки. Не заявляется удаленная RCE.

Исправление: execFile/spawn с argv без shell для проверки отдельного файла; platform-specific безопасный wrapper лишь там, где shell реально необходим.

### A13 · P2 — сообщение теряется из очереди при смене проекта

`src/agent/engine.ts:425–432`.

shiftQueue вызывается до проверки projectId. Если пользователь ушел из A во время хода, queued message уже удалено, но send не планируется. Harness: очередь пуста, запрос сделан только для текущего хода.

Исправление: сначала проверить адресата/доступность запуска, dequeue при атомарном принятии задачи; сохранять очередь при неоткрытом проекте.

### A14 · P2 — Stop в паузе очереди не отменяет запланированный запуск

`src/agent/engine.ts:29–32,425–432`.

После shiftQueue setTimeout на 350 мс не сохраняется в состоянии cancellation. Когда controller уже удален, Stop и clearQueue не отменяют захваченное сообщение. Harness: после stop/clear запущен второй model request.

Исправление: timer belongs to chat generation; stop отменяет pending timers и очередь, callback rechecks token/project.

### A15 · P2 — литеральный пример протокола в code fence интерпретируется как действие

`src/agent/protocol.ts:20–106`.

OPEN ищет action tags по всему тексту, не исключая обычные fences без file-path. Ответ модели с примером команды в документации может стать действием, а не текстом. Harness подтвердил классификацию op; это проверка парсинга, не выполнение команды/действия во внешнем проекте.

Исправление: явный structured tool protocol, однозначно отделенный от markdown; либо lexer состояния fences и escape для примеров. Не ломать намеренный file-path code-fence fallback.

### A16 · P2 — оборванный exec stream возвращает успех без exit frame

`src/lib/backend.ts:219–240`.

code изначально 0, EOF принят без обязательного t=x; остаток buf/финальный decoder flush также не проверяются. Реальная bExec на mock stream только с stderr вернула code0.

Исправление: terminal frame обязательный, EOF/invalid frame => transport failure/unknown result, не code0; раздельно сообщать process exit и завершение связи.

## Приёмка

1. Два конкурирующих хода: завершение старого не меняет новый; Stop прекращает новые эффекты во всех tools.
2. Pending queue timers отменяемы, dequeue не теряет текст при смене проекта.
3. Автоматизация wire prompt/tier/pid строго совпадают с approved specification.
4. Concurrent writes и stale accept/revert сохраняют все стороны изменения либо явно спрашивают о новом конфликте.
5. Backend exec различает preabort, timeout, transport EOF и подтвержденный process exit.
6. Parser отделяет документацию от исполняемых действий; autoVerify не интерпретирует filename как shell syntax.

Ни одно исправление в этом разделе не применялось. Подтверждения здесь — initial harness + повторная сверка кода, не настоящий Windows/provider E2E. Общая очередь исправлений должна объединить связанные причины A03/A04/A11 и A13/A14, но не забыть соответствующие разные regression cases.
