Полный check/build и UI-репродукции повторены после восстановления. Windows, реальные OAuth/SMTP/model providers и browser-IDB failure integration не проверены.

Дата: 2026-10-13. Исходники: `/data/tetrafree`.

## Подтверждённые дефекты

### D01 — P1: копия проекта не отделяется от исходного облака

**Файлы:** `src/store/slices/projects.ts:145–159,166–175`; `src/lib/projectIO.ts:23–30,38–46`. Последствия: `src/lib/team.ts:41–55,490–493,613–626,658–677,801–813`.

**Сценарий:** в Launcher дублировать облачный проект A, затем изменить файл/документ/задачу в копии, считая её независимой. Облачный проект уже должен иметь обычную базу после синхронизации. ZIP-экспорт и повторный импорт дают ту же проблему.

**Причина:** `clone(p)` копирует `cloud` целиком; заменяются локальные `id`, `name`, `path`, но `cloud.pid`, `rev`, `owner`, tombstones и вложенные entity IDs сохраняются. ZIP export/import также сохраняет `cloud`. `tickOnce` отправляет данные по **cloud.pid**, не по новому локальному ID. Кроме того, база облака общая по cloud.pid, а running-lock по локальному pid; две локальные копии не получают общего lock.

**Доказательство D01:** после настоящего duplicateProject и редактирования копии настоящий cloudNow сформировал `PUT /api/team/shared-team` с `main.txt = "COPY PRIVATE EDIT"`. Это адрес исходной команды. Копирование через UI: `src/screens/Launcher.tsx:146–148`. Фоновый проход охватывает даже неоткрытые облачные проекты раз в 20 секунд (`team.ts:807,813`), поэтому ошибка не требует ручного подключения копии к облаку.

**Результат:** «приватная копия» публикует правки участникам A; A и копия конкурируют как две версии одного облачного проекта. Это неверная привязка данных, **не обход серверной авторизации**: воспроизведение предполагает пользователя с действующим доступом к A.

**Направление исправления:** единая операция detach для duplicate/import; очистить cloud и связанные разрешения/локальную синхронизационную идентичность. Новое облако создавать только явно. Если несколько локальных aliases одного cloud.pid намеренны — общий lock и отдельная корректная база для каждого alias.

### D02 — P1: ZIP-импорт затирает исходную папку

**Файлы:** `src/lib/projectIO.ts:28,46`; `src/store/slices/projects.ts:169–175`; путь последствия `src/lib/sync.ts:99–106,164–175,205–206,389–409`.

**Сценарий:** экспортировать A с `path=C:/work/alpha`; позже изменить файл на диске; импортировать старый архив обратно на том же устройстве и открыть новый `alpha-2`. Backend sync включён, backend доступен.

**Причина:** архив содержит исходный абсолютный `path`; importProjectFile возвращает его без очистки, importProject меняет имя/id, но не path. База дисковой синхронизации нового ID пуста. Если обе версии файла есть и различаются, reconcile в ветке `b === undefined` **пишет архивную версию поверх диска**. Проверка «папка уже занята» из NewProject обходится ZIP-импортом. Для сравнения, JSON backup importer правильно сбрасывает `path` и `cloud` (`src/lib/backup.ts:80–86`).

**Доказательство D02:** реальный round-trip exportProject → importProjectFile → importProject сохранил `C:/work/alpha`. Настоящий reconcile отправил bBatch для нового ID в эту же папку с `main.txt="archive-old"`; подставной диск до прохода содержал `"DISK NEWER"`, после — `"archive-old"`. UI-вход: `src/screens/Launcher.tsx:106–111`; открытие автоматически планирует сверку (`sync.ts:389–394`).

**Результат:** новый проект перезаписывает более новые файлы оригинала. Старая дисковая версия не обязательно существует в Git/истории: она могла быть некоммиченной внешней правкой.

**Направление исправления:** очищать path/cloud для импортированного архива; выбирать новую папку явно; централизованно запрещать владение одной нормализованной папкой двумя независимыми проектами.

### D03 — P1: восстановление чата переносит его в другой проект

**Файлы:** `src/store/slices/chats.ts:96–104,135–142`; `src/workspace/Sidebar.tsx:327–337`; `src/store/slices/ui.ts:90–98`; `src/components/Toasts.tsx:28–34`.

**Сценарий:** удалить приватный чат в A, переключиться в B, нажать «Вернуть» в ещё видимом тосте (время жизни действия — 5,2 секунды).

**Причина:** callback хранит только chat и index. restoreChat вызывает `find(s)` без pid, вставляет чат в **текущий** проект и снимает tombstone только там. Тосты глобальные и не привязаны к исходному проекту.

**Доказательство D03:** deleteChat в A → openProject B → restoreChat(copy,0): `AChatCount=0`, в B появляется `SECRET A` с конфиденциальным сообщением; tombstone A остаётся. Ни клонирования проекта, ни совпадающих ID для этого дефекта не требуется.

**Результат:** исходный чат не восстановлен; его история оказывается в B, и при облачной синхронизации B может стать доступна другой команде.

**Направление исправления:** callback/restoreChat должны принимать исходный pid; если исходный проект удалён — отказ с объяснением, не перенаправление на текущий.

### D04 — P1: Markdown-импорт меняет назначение во время ожидания

**Файлы:** `src/lib/mdfiles.ts:9–15,28–31`; `src/store/slices/docs.ts:9–21`. UI-вход: `src/modals/Palette.tsx:483–484`.

**Сценарий:** в A запустить импорт папки/нескольких .md; после выбора файлов переключиться в B, пока асинхронные File.text() ещё не завершены. Последовательное чтение до 300 файлов делает этот промежуток достижимым без искусственного размера файла.

**Причина:** исходный pid не захватывается ни при запуске, ни при onchange. После всех await вызывается addDocs, который выбирает текущий projectId.

**Доказательство D04:** тест отложил File.text, переключил A → B и завершил чтение `# Private A`. В A документов 0, в B создан `Private A`. Парсер и addDocs реальные.

**Результат:** документы попадают в чужой проект и могут автоматически уйти его команде; сообщение «Импортировано» не сообщает о смене назначения.

**Направление исправления:** захватывать исходный pid при запуске и передавать в addDocs; перед записью проверять существование исходного проекта.

### D05 — P1: открытая форма задачи откатывает чужие изменения

**Файлы:** `src/modals/Forms.tsx:510–522,564–581`; `src/store/slices/tasks.ts:22–30`.

**Сценарий:** открыть задачу; коллега/агент изменяет её описание, статус или исполнителя; изменение приходит в store, пока форма остаётся открытой. Сохранить своё изменение одного поля либо просто нажать «Сохранить».

**Причина:** editable поля useState инициализируются только при первом рендере. Даже после обновления orig форма сохраняет **все** старые значения через Object.assign. Нет base revision, dirty-field patch или проверки конфликта.

**Доказательство D05:** реальный TaskModal открыл Old title/Old desc/backlog. Реальный saveTask поставил REMOTE title/REMOTE desc/done. Повторный рендер формы сохранил её hook-state; настоящий save callback вернул Old title/Old desc/backlog и обновил timestamp. Это отдельный дефект формы, не D07: он проявляется уже после того, как чужая правка успешно попала в локальный store.

**Результат:** чужая работа и статус выполнения теряются без предупреждения; новый timestamp делает старую форму более свежей для облака.

**Направление исправления:** сохранять только dirty fields относительно открытого baseline; для изменившихся снаружи dirty fields показывать конфликт; не откатывать нетронутые поля.

### D06 — P1: вставка картинки после смены проекта пишет не в исходный документ

**Файлы:** `src/workspace/DocView.tsx:62–84,433–438`; `src/store/slices/docs.ts:39–45`; `src/store/slices/projects.ts:149,169–175`.

**Сценарий:** создать обычную копию A → B (вложенные document IDs копируются), открыть документ A и начать вставку изображения; переключиться в B до завершения createImageBitmap/сжатия. У A/B при этом может быть разная команда — например B отсоединён и отдельно опубликован.

**Причина:** fresh() ищет doc.id в **текущем проекте**; updateDoc тоже не получает исходный pid. await не отменяется при размонтировании компонента. У копий/imported projects одинаковые doc.id — это штатная операция, не искусственная коллизия случайного генератора.

**Доказательство D06:** отложен shrinkImage, после openProject B он завершён. В A остался 1 блок; в документ B добавлен `data:image/png;base64,A_SECRET_IMAGE` после его собственного `B text`. Использованы настоящие addImages/fresh/updateDoc. Наличие общих IDs воспроизведено в модели состояния, а сохранение этих IDs обычным duplicate/import подтверждается D01/D02 и исходником.

**Результат:** приватная картинка A попадает в B. Если в B нет такого doc.id — результат вставки вообще молча теряется (fresh даёт [], updateDoc ничего не находит), без сообщения об ошибке.

**Направление исправления:** захватывать pid вместе с doc.id; fresh/updateDoc адресовать им; при удалении исходного документа прекращать вставку с уведомлением, а не искать аналог в текущем проекте.

### D07 — P1: независимые правки документа/задачи теряются при облачном merge

**Файлы:** `src/lib/team.ts:377–389,435–450,548–553`; формирование данных `src/store/slices/docs.ts:43–45`, `src/store/slices/tasks.ts:30`.

**Сценарий:** два участника от общего состояния редактируют разные абзацы одного документа либо разные поля одной задачи до синхронизации. У одной записи updatedAt чуть позже.

**Причина:** mergeSet заменяет **весь объект** по одному updatedAt. Для документов нет слияния по block.id, для задач нет слияния полей/comments/subtasks. В конфликтной ветке местный объект полностью выбрасывается; обе версии не сохраняются и конфликт не обозначается.

**Доказательство D07:** настоящему applyMeta переданы local task title=`LOCAL title` и remote desc=`REMOTE desc` от общего исходного task с timestamp 100/101. Итог — Old title + REMOTE desc: локальный title потерян. Аналогично local изменил блок b1, remote b2: итог сохранил remote b2, но вернул b1 к исходному тексту. `unchanged=false`, то есть выполнена именно ветка конкурентных изменений, а не простое принятие чужой версии.

**Результат:** тихая потеря независимой работы, включая целые блоки, подзадачи и комментарии, если они принадлежат проигравшему объекту. Для документов/задач нет аналогичного файлам `.cloud` или diff3 пути восстановления. Это не претензия к отсутствию CRDT: достаточно сохранить обе конфликтные версии или слить независимые элементы.

**Направление исправления:** merge по block.id/field/subtask/comment с общим baseline либо явные конфликтные копии. Нельзя выдавать whole-object LWW за безопасное слияние документов/задач.

### D08 — P2: debounce инспектора теряет последнюю правку при смене страницы

**Файлы:** `src/design/Inspector.tsx:536–543`; `src/design/actions.ts:50–70,95–98`; смена страницы `src/design/Studio.tsx:86–104`; кнопки страниц `src/design/Layers.tsx:149–161`.

**Сценарий:** изменить текст простого блока в Inspector и менее чем через 220 мс выбрать другую страницу, либо дождаться внешней правки и перезагрузки DOM до debounce.

**Причина:** timeout захватывает старый el. Нет flush/cancel на unmount или смену el/страницы. setText меняет старый, уже отсоединённый DOM, но commitDoc сериализует **текущий** useDesign.doc/page. Исходный файл не получает последнего текста.

**Доказательство D08:** вызван настоящий TextBox.onChange(`A LAST EDIT`), затем design.doc/page переключён на B и выдержано 260 мс. Старый el получил `A LAST EDIT`, а сохранённый `site/a.html` остался `A original`; B также не изменился. Для теста DOM/serialize — минимальная модель, реальный браузерный lifecycle не запускался. Потеря непосредственно следует из реально выполненной связки push → setText → commitDoc и из сброса doc при смене страницы в Studio.

**Результат:** последнее введённое значение исчезает из файла; оно не было сохранено, поэтому история версий не помогает.

**Направление исправления:** flush в исходный документ до смены контекста, либо write с захваченными pid/page/doc и валидацией версии. Простая отмена таймера при смене страницы предотвращает неверную запись, но сама по себе всё ещё теряет введённый текст.

## Гипотезы — НЕ включены в 8 подтверждённых дефектов

1. **UiLib: stale package.json после сетевого ожидания.** `src/modals/UiLib.tsx:204–207`: addDeps получает старый p.files['package.json'], ждёт npmLatest и пишет весь результат. Возможна потеря изменения package.json от агента/диска во время запроса. `prepare:171–179`/`apply:193–201` также держат старый план файлов. Нужна отдельная репродукция с реальным addDeps и задержкой ответа, а также проверка UX подтверждения изменившегося плана. Не выдаётся за выполненный тест.
2. **ZIP и бинарные/не-UTF8 файлы.** `src/lib/zip.ts` декодирует содержимое файлов как UTF-8, а экспорт кодирует строки обратно. Нужны отдельная проверка допустимости бинарных файлов в продукте и byte-for-byte репродукция через UI-путь обычного ZIP. Не включено как подтверждённая потеря данных этого аудита.

Не заявляется обход прав доступа через sandbox preview: Canvas разрешает same-origin **без scripts** (`src/design/Canvas.tsx:414`), Preview разрешает scripts **без same-origin** (`src/design/Studio.tsx:484`), UiLib preview также без same-origin (`src/modals/UiLib.tsx:322`). На основании этих участков готового sandbox escape нет.

## Рекомендуемый порядок исправлений

1. D01/D02: безопасное отделение копии/импорта от облака и папки оригинала.
2. D03/D04/D06: явный pid для всех callback/await, исключить переназначение на текущий проект.
3. D05/D07: сохранение по изменённым полям и конфликтобезопасное слияние записей.
4. D08: flush отложенного ввода до смены design context.

Ни одно исправление не применено; отчёт и репродукции находятся только в каталоге аудита.
