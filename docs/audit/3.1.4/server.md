# TetraFree: аудит серверной безопасности и надежности

> Этот раздел уже содержит точную историю восстановления и степень доказательств. Код приложения не исправлялся.

## Область, состояние и достоверность

Проверены `server/tetra-server.mjs`, `auth.mjs`, `secrets.mjs`, `mcp.mjs`, `web.mjs`, `mail.mjs`, `folders.mjs`, `gitremote.mjs`, `editors.mjs` и вспомогательные модули обхода/игнорирования/резервных копий/Git. `pty.mjs` и `conpty-win.mjs` исключены: их проверял другой агент. Небольшие фрагменты frontend и `vite.config.ts` прочитаны только для установления достижимости серверного превью.

Это **аудит, не исправление**. Код проекта не изменялся, push не выполнялся. В рамках этой работы HTTP/SMTP/MCP-серверы не запускались, `start()`/`listen()` не вызывались. Динамические проверки использовали искусственные учетные записи, временные пути, вызов middleware внутри процесса и поддельные транспорты; никаких внешних целей или реальных секретов.

**Восстановление отчета:** после первоначальных проверок среда была сброшена. Первые скрипты, логи и временные фикстуры утрачены. Данный отчет восстановлен по наблюдавшимся результатам инструментов и повторному чтению доступных исходников. После сброса тесты **не повторялись**, новые эксплуатационные проверки не проводились. Хеши доступных после сброса исходников сохранены рядом в `server-source-hashes-restored.txt`; прежний файл хешей утрачен, полное побайтовое сравнение снимков невозможно. Существенные участки кода повторно сверены.

### Уровни доказательств

- **Code:** дефект прямо следует из проверенной ветки исходника. Это не доказательство полного сценария в браузере, ОС или внешнем сервисе.
- **Mock:** результат наблюдался при поддельном запросе/транспорте/клиенте, без реального сетевого обмена.
- **Native fixture:** выполнены настоящие файловые операции, URL parsing, scrypt/AES на искусственных данных Linux. HTTP-вход в таких проверках оставался внутрипроцессным mock.

Первоначальный набор из **8 проверок завершился 8/8**: наблюдения совпали с утверждениями тестов. Это **не означает «безопасность прошла тесты»**: несколько утверждений специально фиксировали дефект. Отдельно завершилась SMTP-проверка на mock-транспорте. Последующее добавление проверок Git и HTTP response ID в MCP не было запущено до сброса; они ниже не выдаются за динамически подтвержденные.

Приоритеты: **P1** — исправить до доверенного использования соответствующей функции; **P2** — следующая очередь исправлений/уточнения границ. P0/подтвержденная удаленная неаутентифицированная RCE не заявляются.

## Подробные находки

### S01 — нет серверной origin isolation для недоверенного превью

**Приоритет:** P1 для браузерной установки, где приложение и серверное превью находятся на одном origin.

**Код:**
- `server/tetra-server.mjs:1171–1206`: HTML из папки проекта отдается как `text/html` без CSP/sandbox и отдельного origin.
- `server/tetra-server.mjs:1252–1280`: standalone-сервер отдает приложение на том же HTTP-сервере; заголовки статического приложения не распространяются на ветку превью.
- `vite.config.ts:7–12`: серверные маршруты встраиваются в origin Vite.
- `src/lib/backend.ts:190–195`: URL превью использует адрес backend либо `location.origin`.
- `src/design/Studio.tsx:288–295`: есть штатное открытие этой страницы во внешнем браузере.
- `src/lib/token.ts:2–14`: Bearer хранится в origin-local `localStorage`.
- `server/auth.mjs:250–253`: preview capability проверяется относительно сессий, а не конкретной страницы/проекта.

**Достижимый сценарий:** пользователь браузерного приложения открывает серверное превью недоверенного или измененного другим участником HTML. Открытая верхнеуровневая страница не получает ограничений sandbox обычного iframe и находится на origin приложения.

**Последствия:** проектный JavaScript получает браузерные права origin приложения, включая доступ к его origin-local данным. Это нарушает границу между «посмотреть сайт проекта» и «доверенный интерфейс управления приложением». Если на этом origin есть действующий Bearer, риск касается его конфиденциальности и авторизованных функций backend. Это условное следствие браузерной модели, **не выполненная цепочка получения токена или выполнения команд**.

**Доказательство:** проверены выдаваемые заголовки и связи frontend/server. Browser exploit не строился. Наличие sandbox у встроенного `srcDoc`-iframe не защищает отдельно открываемый серверный документ. В Tauri frontend и внешний системный браузер могут иметь разные origin и хранилища; автоматический перенос desktop-Bearer в системный браузер **не доказан и не заявляется**.

**Рекомендация:** выделить для project content отдельный origin без доступа к API/хранилищу приложения. Использовать ограниченную проектом и сроком capability для превью. Если интерактивность не нужна — серверная sandbox-CSP без script execution; если нужна — отдельный origin и минимальная CSP. Не считать URL path или `noopener` заменой origin isolation. Исключить обслуживание чувствительных служебных файлов как превью. Учесть, что session-wide preview token также не является изоляцией проектов друг от друга.

### S02 — итоговый index-файл не проходит проверку symlink containment

**Приоритет:** P1.

**Код:** `server/tetra-server.mjs:1188–1206`, особенно `1190–1191` и `1196`.

**Root cause:** `inside()` и `realInside()` проверяют исходный путь. После успешной проверки, если он оказался каталогом, к нему добавляется `index.html`. Новый файловый путь сразу передается в `pipeFile()` без повторной проверки.

**Достижимый сценарий:** в проекте есть нормальный внутренний каталог, но выбранный в нем index-файл — ссылка на читаемый файл за пределами проекта. Такое состояние возможно при локальных изменениях или недоверенных файлах проекта. Поддержка ссылок и права различаются между ОС.

**Последствия:** выдача содержимого внешнего файла через ограниченное превью вместо отказа в доступе. Для этой ветки требуется локальное соединение и действующая preview capability, но не обычный Bearer. Возможная чувствительность файла зависит от прав backend.

**Доказательство:** до сброса на Linux создан искусственный sibling-sentinel и ссылка на него из временного проекта. Прямое обращение к итоговому файлу было отклонено с 400. Выбор того же файла через каталог дал 200 и содержимое sentinel. Настоящие symlink/read операции + mock request/response; TCP-сервер не запускался.

**Рекомендация:** сначала полностью определить конечный файл, затем выполнить containment и проверку типа файла непосредственно перед открытием. Общий helper должен возвращать проверенный конечный путь/дескриптор, а не разрешать последующие невалидированные изменения пути. Отдельно проработать TOCTOU; просто перенос проверки устраняет наблюдавшийся deterministic defect, но не доказывает race-free filesystem sandbox.

### S03 — неполная нормализация IPv4-mapped IPv6

**Приоритет:** P2. Нарушает заявленную защиту web-fetch от внутренних адресов; не означает анонимный доступ к сетевым функциям.

**Код:** `server/web.mjs:19–34`, `52–59`, `63–77`, `89–106`.

**Root cause:** mapped IPv6 распознается только в одной текстовой форме с dotted IPv4-tail. Стандартный URL parser может канонизировать этот же адрес в hex-группы. IPv6-ветка для такой формы возвращает `false` — «не приватный».

**Достижимый сценарий:** локальный авторизованный web-fetch получает IPv4-mapped IPv6 адрес, который семантически относится к запрещенному IPv4 диапазону. Форма может поступить из пользовательского адреса или проверяемых DNS-результатов.

**Последствия:** решение security validator не соответствует реальному классу адреса; предпосылка доступа web-fetch к внутреннему HTTP-сервису вопреки документации. Какой конкретно сервис ответит и доступны ли эти адреса на целевой ОС — не проверялось.

**Доказательство:** native `URL` и экспортированные validators на искусственных адресах: обычный IPv4 loopback отклонялся; его mapped IPv6 каноническая форма классифицировалась как публичная и принималась `checkUrl()`. DNS/HTTP connection, редиректы и реальный доступ к службе не выполнялись.

**Рекомендация:** разбирать адрес в бинарное/каноническое представление; mapped адреса переводить в IPv4 перед проверкой диапазонов. Применять единый classifier к literal URLs и всем DNS candidates; покрыть разные семантически эквивалентные записи unit-тестами. Проверить reserved, multicast и transition ranges отдельно, не полагаясь на текстовые префиксы как общий IP parser.

### S04 — потеря владения pending-registration credentials

**Приоритет:** P1, касается неподтвержденных аккаунтов.

**Код:** `server/auth.mjs:520–539`, `554–563`; также `issueCode/checkCode` на `257–278`.

**Root cause:** при совпадении email блокируется только `ex.verified`. Неподтвержденная запись повторно используется, и `name`/`passHash` заменяются параметрами нового неаутентифицированного запроса. Подтверждение email хранится отдельно по адресу, без привязки к конкретной транзакции регистрации/версии credentials.

**Достижимый сценарий:** повторная регистрация на адрес уже ожидающей подтверждения записи до завершения email verification. Новый запрос не доказывает знание прежнего пароля или владение email. Подтверждение адреса впоследствии относится к текущему состоянию записи, а не обязательно к credentials, введенным владельцем при первоначальной регистрации.

**Последствия:** подтвержденная в тесте неавторизованная замена pending-пароля/имени и сбой завершения регистрации; потенциальная несовместимость email ownership и password ownership. Полная цепочка захвата аккаунта **не выполнялась и не публикуется**. Уже подтвержденная запись обычной этой веткой не заменяется.

**Доказательство:** synthetic pending-user заранее имел искусственный scrypt-hash. Router с другим паролем на ту же pending-запись вернул 201. После `flushDb()` сохраненный hash соответствовал новому паролю, а прежний hash был заменен. Реальные scrypt/JSON-файл в фикстуре + mock io; без реальной почты, входа или account takeover.

**Рекомендация:** не менять pending credentials повторным register-запросом. Повторная отправка письма должна быть отдельной операцией без перезаписи пароля. Привязать challenge к registration transaction, user ID и версии credentials; завершать регистрацию атомарно. Если переоформление pending-записи требуется продуктом — разрешать его только после email proof, с явным безопасным восстановлением.

### S05 — локальная TOTP-политика не применяется к OAuth

**Приоритет:** P1 при настроенном GitHub/Google OAuth и включенной TOTP у соответствующего пользователя.

**Код:** `server/auth.mjs:695–719`, `724–730`; контраст с password login `600–608` и password reset `657–662`.

**Root cause:** OAuth callback получает/связывает пользователя и создает exchange ticket. Exchange вызывает `newSession()` без ветки `user.totp?.enabled`. Password login/reset такую ветку имеют.

**Достижимый сценарий:** существующий verified-user с включенной TetraFree TOTP входит через настроенного OAuth provider. Успешный OAuth подтверждает provider identity, но сервер не требует дополнительный фактор, включенный именно в TetraFree.

**Последствия:** разные способы входа применяют разные требования локальной 2FA. Подтверждение у провайдера не является доказательством, что настроенный в TetraFree фактор выполнен; нельзя предполагать наличие MFA у каждого внешнего аккаунта.

**Доказательство:** прямой анализ ветвей, включая unconditional `newSession()` в exchange. Реальные OAuth credentials, callback у провайдера и браузерный вход не проверялись. Это **code-confirmed отсутствие проверки**, не наблюдавшийся takeover.

**Рекомендация:** все методы входа должны сходиться в единую post-authentication функцию: проверить локальную TOTP-policy, при необходимости вернуть limited MFA ticket и лишь после этого создавать полную сессию. Если OAuth сознательно исключается из 2FA, явно описать этот продуктовый контракт и не обещать локальный фактор «при любом входе».

### S06 — SMTP допускает cleartext fallback

**Приоритет:** P1 для соединений `smtp://` вне заведомо доверенного локального relay. Для `smtps://` этот конкретный fallback не применяется.

**Код:** `server/mail.mjs:45–55`, `94–124`, `125–139`.

**Root cause:** STARTTLS выполняется только если capability присутствует. Отсутствие этой capability не считается ошибкой: код продолжает AUTH PLAIN/LOGIN и передачу письма через исходный `net.connect()`.

**Достижимый сценарий:** `smtp://` сервер не предлагает STARTTLS либо capability отсутствует из-за недоверенного сетевого посредника. Код не требует шифрования до отправки credentials и тела сообщения.

**Последствия:** раскрытие SMTP credentials и содержимого писем на незашифрованном транспорте. Письма приложения могут содержать verification/reset codes; сами payloads передачи и сценарии злоупотребления ими здесь не публикуются.

**Доказательство:** отдельная mock SMTP state-machine с искусственными credentials и письмом, без STARTTLS capability, дошла до AUTH и принятого DATA; `sendMail()` сообщил `sent`. Перехвачены вызовы `write()` поддельного `net.connect()`; реального сокета, SMTP listener, MITM и TLS handshake не было.

**Рекомендация:** для authenticated SMTP обязательный TLS: либо implicit TLS, либо STARTTLS с hard failure при отсутствии/неуспехе upgrade. Запрещать AUTH до завершения TLS и проверки сертификата. Если cleartext нужен для локального dev relay, вводить отдельный явный opt-in с предупреждением и ограничением адреса, не включенный по умолчанию.

### S07 — filesystem containment применяется не ко всем операциям

**Приоритет:** P2. Требуется локальный авторизованный доступ; это не удаленное неаутентифицированное удаление файлов.

**Код:**
- `server/tetra-server.mjs:675–679`: rmdirs вызывает только lexical `inside()`, затем `fsp.rmdir()`/`pruneEmpty()`.
- `server/tetra-server.mjs:198–207`: `pruneEmpty()` тоже использует строковую границу пути.
- `server/tetra-server.mjs:839–842`: Git `relOk()` проверяет lexical containment, но не разрешение symlink.
- `server/tetra-server.mjs:921–926`: untracked diff обращается к filesystem через Git.
- `server/tetra-server.mjs:966–975`: untracked discard вызывает `fsp.rm(inside(...))` без `realInside()`.

**Root cause:** написанный для защиты от symlink helper применяется к write/read и ряду других ветвей, но пропущен в некоторых destructive/read operations.

**Достижимый сценарий:** внутри проекта присутствует ссылка на внешний каталог, а файловая операция выбирает дочерний путь через эту ссылку. Lexical путь находится «внутри», реальный объект — нет.

**Последствия:**
- **Подтверждено для rmdirs:** удаление внешнего пустого каталога при правах backend. `rmdir` не рекурсивный, поэтому удаление непустого дерева **не заявляется**.
- **Для Git по code:** filesystem-путь untracked diff/discard не проходит эквивалентную containment-проверку; чтение/удаление через symlink-parent требует отдельного native Git regression test. Эта часть **не выдаётся за уже воспроизведенный Git leak/delete**.

**Доказательство:** до сброса в synthetic Linux filesystem `realInside()` отклонил дочерний путь через ссылку, но rmdirs-маршрут с mock HTTP вернул 200, и искусственный внешний пустой каталог исчез. Проверка Git была только добавлена в тестовый файл, но не запущена до сброса.

**Рекомендация:** единые helpers для чтения, записи и удаления, включающие real containment. При удалении самой ссылки проверять родителя и не следовать ссылке; при операции над дочерним объектом проверять разрешенные промежуточные компоненты. Применить ту же политику к `pruneEmpty()` и Git-веткам. Не подавлять все ошибки destructive operations без видимого диагностического результата.

### S08 — MCP initialization race в пуле

**Приоритет:** P2, надежность и порядок протокольных операций; самостоятельное повышение привилегий не доказано.

**Код:** `server/mcp.mjs:432–449`, особенно `433–434` и `440–443`; использование клиентом router на `511–538`.

**Root cause:** клиент попадает в `pool` до завершения `await c.start()`. Второй параллельный `get()` видит объект и немедленно его возвращает, не ожидая initialization первого вызова.

**Достижимый сценарий:** одновременно приходят запросы инструментов/вызова инструментов одного одобренного MCP server на холодном соединении.

**Последствия:** запрос может уйти до завершения initialize/initialized; возможны отказы, нарушение negotiation и ошибки при неуспешном startup. Конкретное поведение зависит от MCP-сервера. Наличие side effects до initialization не выполнялось и не утверждается.

**Доказательство:** mock клиент с управляемым Promise в `start()`: второй `get()` завершился с тем же клиентом, пока `start()` первого еще был заблокирован. Никакой дочерний процесс/MCP server не запускался.

**Рекомендация:** хранить single-flight initialization promise вместе с клиентом и ожидать его при каждом `get()`. Разделить состояния starting/ready/failed/closed. При ошибке/отзыве разрешения синхронно отклонять всех ожидающих и корректно удалять только соответствующее поколение записи пула.

### S09 — нет correlation check у HTTP JSON MCP response

**Приоритет:** P2, целостность протокола/результатов; не отдельный exploit против чужой системы.

**Код:** `server/mcp.mjs:334–364`, особенно `361–364`. В SSE-ветке `350–351` ID сверяется, в JSON-ветке — нет.

**Root cause:** после `res.json()` принимается произвольный truthy reply; далее проверяется только `.error`, возвращается `.result`. Поля `jsonrpc`, matching `id` и ожидаемая форма результата не валидируются.

**Достижимый сценарий:** одобренный HTTP MCP endpoint или промежуточный компонент возвращает не относящийся к запросу JSON reply, например из-за ошибочного routing/cache/multiplexing.

**Последствия:** чужой результат может быть присвоен текущему запросу; некорректные ответы проходят слишком далеко и превращаются в неоднозначные downstream errors. Сам по себе этот дефект не доказывает доступ неразрешенного MCP server.

**Доказательство:** Code. Mock-тест с unrelated response ID был написан в утраченный файл, но до сброса **не запускался**. Поэтому динамический результат здесь не заявляется.

**Рекомендация:** общая JSON-RPC response validation для JSON и SSE: версия, matching ID, корректный тип result/error; отклонять notification/unrelated response. Установить общий inbound size limit до полного parsing, а не только обрезание итогового текста после получения ответа.

## Что не включено в список подтвержденных уязвимостей

1. **«Любая shell-команда / произвольная папка» сама по себе не finding.** Приложение сознательно предоставляет локальному авторизованному пользователю shell, работу с выбранными папками и custom editor. Без пересечения новой доверительной границы это не RCE/произвольная файловая уязвимость.
2. **`/api/proxy` с произвольным URL не назван отдельно доказанной SSRF.** Эта ветка предназначена для локальных провайдеров, уже требует local+auth. Её unrestricted URL/redirect policy отличается от ограниченного web-fetch; стоит документировать это различие и разграничить возможности агента, но техническая возможность доступа к локальному провайдеру может быть намеренной.
3. **MCP approval hash и executable integrity:** hash включает абсолютную папку, имя, raw cfg. Он не фиксирует expanded environment и содержимое исполняемого файла/скрипта. В unit-check hash менялся от folder/command, а разные environment values давали разные resolved config при том же raw hash. Это доказанное свойство дизайна, но без утвержденного контракта «одобряется неизменный бинарник» не выдается за готовый approval bypass.
4. **MCP/shot inbound memory limits:** есть накопление stdout/CDP/SSE/JSON до ограничения результата. Это риск hardening/resource exhaustion, но OOM/DoS не вызывался и не доказан отдельным stress test.
5. **TOCTOU filesystem:** `realInside()` не создает race-free sandbox. Смена ссылки между проверкой и открытием возможна концептуально; специальная гонка не строилась.
6. **OAuth state browser binding:** state хранит expiry/back, без browser-bound verifier. Нужна отдельная проверка login-CSRF/session binding и PKCE strategy. Действующая login-CSRF/перенос callback между браузерами не проверялись и не заявляются доказанными.
7. **Секреты на Unix:** AES key рядом с ciphertext — явно описанный разработчиком fallback, не защита от пользователя, который читает оба файла. Это не неожиданная криптографическая уязвимость.

## Положительные проверки и уже имеющиеся ограничения

- Host/Origin filtering, local socket check и Bearer gate присутствуют. На mock requests внешний Origin дал 403, non-loopback — 403 для файлового маршрута, отсутствие Bearer — 401.
- `realInside()` действительно отклоняет обычные выходы через symlink при прямом выборе итогового файла. Основная проблема — покрытие всех ветвей и выбор final path.
- В auth применены scrypt, random tokens, hash-at-rest sessions, TTL/rate limits/code attempt limits и TOTP replay tracking. Они не исправляют разницу требований между отдельными способами входа.
- Git запускается с массивами аргументов, многие file/path аргументы защищены `--`; remote URL ограничен протоколами и отсутствием явной option/shell-form. Универсальная command injection здесь не доказана.
- Windows PowerShell vault передает данные через environment, скрипт статический. Windows DPAPI нативно не проверялся.
- Native synthetic Unix vault roundtrip прошел; свежие `secrets.key`/`secrets.json` имели 0600, plaintext-секрет отсутствовал в blob-файле. Это не проверка разрешений уже существовавших файлов, symlink races или Windows backend.
- Dev outbox намеренно доступен только local+dev; его отсутствие обычного Bearer само по себе не отмечено как удаленная уязвимость.

## Рекомендуемая очередь исправления и защитной приемки

1. Изолировать server preview от origin приложения; ограничить preview capability проектом/сроком и исключить служебные файлы.
2. Исправить проверку конечного `index.html` и унифицировать containment во всех read/delete/Git paths.
3. Устранить перезапись pending credentials; централизовать post-login MFA для password/OAuth/reset.
4. Сделать TLS обязательным для SMTP credentials/verification mail.
5. Заменить текстовый IP classifier на корректный semantic parser.
6. Исправить MCP initialization single-flight и JSON-RPC correlation/size validation.

Защитная приемка должна использовать только искусственные проекты/аккаунты: отклонение итогового symlink-file; одинаковый отказ всех файловых операций на внешние объекты; невозможность менять pending password повторной регистрацией; обязательный TOTP gate на всех методах входа; отказ SMTP до AUTH без TLS; единая классификация эквивалентных IP; ожидание MCP readiness всеми параллельными consumers; отказ unrelated RPC IDs. Проверку на целевой Windows/desktop и реальные provider configurations выполнять отдельно и с явным разрешением.

## Ограничения аудита

- Нельзя называть этот результат полным pentest или исчерпывающим доказательством отсутствия других багов.
- Первичные результаты наблюдались до сброса; их отдельные артефакты не сохранились. Тесты после восстановления не запускались.
- Не запускались сервер, эксплуатационные браузерные payloads, account takeover chains, реальные OAuth/SMTP/MCP endpoints, private network probing.
- Нет native Windows DPAPI, cmd.exe parsing, NTFS junction/ADS/device semantics и conpty/pty: часть вне области, часть не доступна в Linux.
- Не выполнены стресс-тесты памяти, гонки файловой системы, большие/медленные ответы, одновременные auth-транзакции или сценарии падения питания.
- Точные последствия Git symlink branches и MCP wrong-ID требуют будущих defensive regressions; здесь только source evidence.
- Desktop Browser/WebView storage separation и реальные глобальные CSP среды не измерялись. P1 для preview указан с точным условием same-origin web deployment.
- Для отдельных находок обязательны local+auth либо preview capability, TLS-mode configuration или настроенный OAuth. Эти условия нельзя убирать из итогового пересказа.
- Package заявляет 3.1.4; предоставленная копия не имеет доступного Git commit identity. Хеши восстановленного source snapshot сохранены, но они не заменяют утраченные исходные логи.
