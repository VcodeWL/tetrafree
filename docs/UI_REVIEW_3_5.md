# TetraFree — независимая критическая UI/UX-оценка

Дата: 21 октября 2026. Объект: `/data/tetrafree-ui`, dev `http://127.0.0.1:3010`.

## Краткий вывод

**Основная оболочка и чат визуально собраны лучше, чем сквозные сценарии управления. До заявления о готовности всего UI нужно закрыть три P1: клавиши дизайнера проходят сквозь модальные окна, общее меню недоступно с клавиатуры, мобильная студия получает нулевую ширину холста.** Форма задачи также допускает тихую потерю некорректно введённой даты. Проблема мобильного launcher найдена в ходе оценки, исправлена другим участником и независимо перепроверена — в открытый backlog она не включена.

Серо-сиреневая гамма, исходное фоновое изображение и широкая плавная декоративная лента соответствуют заданному направлению. Нет оснований менять их на другую концепцию ради «улучшения UX». Приоритет — поведение и доступность, затем локальная визуальная доводка.

## Метод и границы

- Исходники не редактировались, push/build/install не выполнялись, сервер и чужие процессы не останавливались. Созданы только этот отчёт, независимые тестовые скрипты, JSON и снимки в `/data/tetrafree-ui-qa`.
- Все исходные восемь `final-*.png` из задания просмотрены через `view_image` по одному. Дополнительно просмотрены независимые снимки основных семейств, ошибок и воспроизведений. Позже отдельно просмотрен `final-launcher-mobile.png`.
- Runtime: отдельный sandbox-local Chromium через Playwright, не shared browser. Чистые изолированные контексты; все `/api/*` и внешние HTTP-запросы блокировались. Поэтому offline-состояния здесь **намеренно вызваны тестом**, а не доказательство неисправности рабочего сервера.
- После hydration использован `window.__tf`: создана синтетическая модель проекта/чата/задач/документа и статический HTML в памяти тестового браузера. Это не реальная авторизация, не работа с пользовательским проектом на диске. Никакие настоящие провайдеры, ключи, Git-команды или shell-команды не запускались. Контексты закрыты.
- Фикстура подтверждает, что компонент отображается и как обрабатывает события; **не подтверждает**, что пользователь может пройти весь путь до него без аккаунта/бэкенда.
- Доказательства: `independent-runtime.json`, `independent-critical.json`, `independent-followup.json`; скрипты рядом с одноимёнными `.cjs`. Прежний `browser-results.json` использован только как контекст, его успешные тесты не выдаются за независимую повторную проверку.
- Код менялся другим участником во время оценки. Исправление launcher подтверждено на новой версии. Ссылки `file:line` относятся к прочитанной версии; при последующих правках ориентироваться также на имя компонента и воспроизведение.

## 2. Оценки по категориям

Оценки качественные: **сильная основа**, **приемлемо с оговорками**, **требует доработки**, **критический пробел**, **недостаточно проверки**. Общий средний балл не вычисляется: хороший цвет не компенсирует потерю данных от клавиши.

| Категория | Оценка и конкретное основание |
|---|---|
| Информационная архитектура / навигация | **Приемлемо с оговорками.** Проект → чаты/документы/планирование понятен, dev/design разделены. Git, browser, deployment, каталог расширений и библиотека компонентов требуют знания разных точек входа. Недоступные меню — уже дефект, а не вопрос вкуса. |
| Визуальная иерархия | **Сильная основа на основных экранах.** Hero ведёт от вопроса к вводу; чат отделяет человека от агента; primary не конкурирует со всеми кнопками. Технические подписи и маленькие иконки верхней панели недостаточно объясняют первый опыт. |
| Композиция / плотность | **Приемлемо на desktop.** Есть воздух и полезный split. В design code режим одновременно тратит место на навигацию, слои, холст, код и пустой inspector; на mobile это становится функциональным провалом. Compact уменьшает прежде всего отступы, не разрушая чат. |
| Типографика | **Приемлемо с оговорками.** Основные сообщения читаются, заголовки различимы. Мета, сроки, file hints и statusbar очень мелкие; сложные технические статусы не стоит оставлять только в таком размере. Увеличение масштаба не проверялось. |
| Палитра / контраст / фон | **Направление удачно, но проверка неполная.** Приглушённая сиреневая тема узнаваема, light не выглядит механической инверсией dark. Исходный фон оставлять. Для длинного текста на фото полезна более стабильная локальная подложка. В design остаются яркие бирюзовые selected-controls; это рекомендация по согласованности, не причина перекрашивать весь продукт. Контраст всех пикселей на фото не сертифицирован. |
| Компоненты / состояния | **Требует доработки.** Единая оболочка modal, видимый focus и disabled есть. Но общие Menu/Segmented не доведены по клавиатурному контракту; общий компонент распространяет дефект на многие сценарии. |
| Формы / валидация | **Требует доработки.** Labels, типы провайдеров, дата руками/календарём, описания есть. Некорректная дата исчезает при сохранении; локальный профиль требует email для изменения имени. Ошибки иногда видны до первого ввода. |
| Empty / loading / error | **Приемлемо с оговорками.** Hero, пустой preview, offline Git и NewProject объясняют зависимость от сервера. UiLib предлагает выбрать компонент при недоступном списке; folder/remote показывают технический `Failed to fetch`. Реальные длительные loading/recovery не прогонялись. |
| Feedback / progress | **Приемлемо по структуре, недостаточно runtime.** Есть operation center, история уведомлений и отдельные статусы хода агента. Декоративная лента корректно не размечена как progress. Фактический live stream и длительные операции не проверены. |
| Анимации / perf / reduced motion | **Сильная основа по управлению движением.** Независимо подтверждены static ribbon при OS/user reduce и скрытие при calm. По коду лента использует CSS transform и паузу в hidden tab. Это не замер FPS/CPU; производительность длинных чатов и больших проектов неизвестна. |
| Клавиатура / семантика / доступность | **Критический пробел.** Manual keyboard нашёл недоступные menuitems и протекание Delete сквозь modal, хотя axe не нашёл нарушений на просканированных состояниях. Есть хороший focus outline, trap и ARIA, но они не равны рабочей клавиатурной модели. |
| Адаптивность | **Неравномерно.** Чат 1100/390 визуально держится, документ и таймлайн доступны в рассмотренных состояниях. Launcher после исправления помещается. Design не адаптирован к 390; mobile appearance сохраняет слишком узкие колонки текста и длинную горизонтальную навигацию. |
| Чат / агент / разрешения | **Хорошая структура, недостаточно проверки безопасности.** Имя агента, tier, части операций, Apply/Reject и отдельный прогресс в коде полезны. «Спросить»/«Эскалация» требуют явной легенды, что именно разрешено. Работа настоящих разрешений не подтверждена. |
| Файлы / редактор / Git / терминал | **Приемлемая оболочка, недостаточно интеграционной проверки.** Панель кода отличима от чата, offline Git честен. Настоящий save/PTY/Git не проверены. Нельзя считать это рабочей IDE только по README и приглашению shell. |
| Задачи / документы | **Приемлемо с конкретным дефектом формы.** Доска, список, сроки, исполнители и блоковый документ внятны. Таймлайн плотный; сложные задачи и таблицы не проверены. Дата в форме — P2 ниже. |
| Настройки / аккаунт / онбординг / каталоги / дизайн | **Требует доработки.** Разделы последовательны, но локальный onboarding ведёт к недоступной 2FA; настройки смешивают немедленное применение части полей и явное «Сохранить». Catalog, UiLib и дизайн имеют разное покрытие, не объединены в ложный pass. |
| Сохранность / понятность статусов | **Модель честная, подача тяжёлая; есть P1.** Разделение памяти/checkpoint/диска/облака сохранять. Термин checkpoint без объяснения плохо работает для пользователя, а на mobile действие сохранения частично за краем. Сквозная сохранность данных не проверена; подтверждённая мутация дизайна под modal требует исправления. |
| Тексты / русский язык | **Приемлемо с редактурой.** Тон прямой и человеческий, но есть «1 требуют внимания», смесь checkpoint/lease/backend и переход с «ты» на «вы» в UiLib. Технические термины допустимы для IDE, но должны объясняться при первом контакте. |

### Что действительно означает axe

В независимом прогоне WCAG 2 A/AA и 2.1 AA-тегов получено **0 зарегистрированных нарушений** для семи состояний: Task с неверной датой, Settings dark, Tasks board, пустой документ, выбранный элемент Design, Settings mobile, Launcher mobile. Результаты сохранены в `independent-critical.json`. В широком runtime-проходе `pageerror` не зарегистрирован.

**Это не сертификат всего UI и не pass функциональной доступности.** Неверная дата, скрытые меню и Delete под modal прошли скан без замечаний. Screen reader, реальные touch-targets, zoom/reflow, все вариации контраста, native и live-операции требуют отдельной проверки.

## 3. Подтверждённые находки

Severity: **P0** — критический блокер с тяжёлыми последствиями; **P1** — серьёзная поломка основного сценария/защиты; **P2** — существенная проблема с обходом или ограниченной областью; **P3** — локальная ясность/полировка. P0 в проверенном объёме не обнаружены — это не доказательство их отсутствия.

### F01 — P1 — Delete изменяет дизайн под открытым модальным окном

## 4. Рекомендации, не смешанные с дефектами

Это экспертные предложения, а не доказанные функциональные поломки:

1. **Сохранить фон, повысить стабильность чтения.** Для длинных agent/doc-текстов дать мягкую нейтральную подложку/локальное затемнение или пользовательский reading-mode. Не заменять исходное изображение и не заливать весь UI непрозрачными карточками. Проверить dark/light на самых светлых и тёмных областях исходного фото.
2. **Показать смысл технических статусов.** «Снимок в приложении», «Файлы на диске», «Облако» с раскрытием деталей понятнее трёх рядовых checkpoint/lease/backend. При этом сохранить строгую раздельность подтверждений. Tooltip не должен быть единственным объяснением на touch.
3. **Облегчить сложные настройки.** На desktop текущая структура приемлема; на mobile поставить контрол под описанием, а не рядом с колонкой шириной в несколько слов. Отдельно зарезервировать место close-button: в проектном mobile-nav она визуально соседствует с текстом «Провайдеры». Перекрытие не объявляется подтверждённым дефектом клика во всех состояниях.
4. **Согласовать дизайнерские акценты.** Яркий cyan выбранных rail-controls и подсказка «Акцент — бирюзовый» живут отдельно от новой серо-сиреневой оболочки. Привести selected/focus к общим токенам; семантические warning/error/success цвета сохранить.
5. **Объяснить полномочия до первого действия.** Возле tier дать короткое «может читать / предлагать / писать / запускать», а перед опасной операцией — объект, объём изменений и последствия. Не делать ленту индикатором полномочий или прогресса.
6. **Не переусложнять первый старт.** Локально начать с проекта и модели, командные функции и advanced security раскрывать по контексту. Скрытие onboarding — полезная возможность, не удалять.
7. **Увеличить touch-цели и важную метаинформацию.** Сначала действия сохранения, close, attach/send и permission CTA. Размер 44 px — полезная цель для touch, но не объявлять автоматически каждую меньшую desktop-кнопку нарушением WCAG без проверки размеров/расстояний.
8. **Единый стиль русского текста.** Сохранить «ты» во всём продукте, либо перейти на другой тон целиком; в UiLib сейчас «смотрите / вставляйте / выберите». Добавить glossary технических терминов вместо тотального запрета англицизмов.

## 5. Что уже хорошо и не следует ломать

- **Приглушённая палитра и исходный фон.** Они дают характер без обязательных насыщенных цветов. Light/dark должны оставаться самостоятельными настройками. Исправлять читаемость локально, а не перепридумывать арт-дирекшн.
- **Декоративная широкая лента.** В runtime `aria-hidden=true`, role progress отсутствует; OS reduce и пользовательский reduce дают `animationName=none`, calm — `display:none`. Не заменять её progressbar и не сужать вопреки запросу пользователя.
- **Фокус на основной работе.** По умолчанию нет лишней правой панели, но «Открыть файлы проекта» заметно доступно. Split остаётся полезным для desktop.
- **Отдельные подтверждения сохранения.** «В памяти», checkpoint, диск, cloud не надо сливать. В recovery-тексте явно говорится о создании отдельной копии, а не о перезаписи; это правильный принцип, хотя реальное восстановление здесь не тестировалось.
- **Осмысленные empty/offline-состояния.** Hero объясняет отсутствие модели; preview — отсутствие страницы; Git и NewProject — зависимость от сервера. Сохранить эту честность, унифицировав качество recovery-действий.
- **Базовые a11y-кирпичики.** Видимый focus, labels, focus trap/return, ARIA-подписи, клавиатурный Resizer и дерево Layers уже есть. Доработать контракты, а не удалять семантику ради чистого axe.
- **Реальные имена и данные.** Не подделывать успешную авторизацию, установленный провайдер, подписку или сохранение ради красивого состояния.
- **ProjectIcon:** новая реализация уже загружалась в live, пользовательские/тематические иконки сохранены условием `name === 'sparkle'` в `src/components/ui/ProjectIcon.tsx:5–10`. Подтверждён факт интеграции, не выдан окончательный арт-вердикт: старые final-снимки не использовать как оценку нового знака.

### PRO badge — только дизайн-концепт до появления entitlement/billing

В этой оценке billing backend независимо не аудирован; по переданному уточнению реального PRO entitlement нет. Поэтому **не добавлять активный PRO-статус, trial, оплату, лимиты или «подписка действует» в работающий интерфейс без источника истины**. Пункт внесён в roadmap этого отчёта, не в исходный `ROADMAP.md` — соблюдён read-only.

- Визуальная идея: компактная градиентная плашка `PRO`, по качеству и аккуратности близкая к Google-подходу, но без копирования фирменного rainbow. Серо-сиреневая база с мягким лавандово-фиолетовым переходом; спокойный статический вариант для calm/reduce, достаточный контраст надписи.
- Основное место в будущем: строка плана в Account. Вторичное: рядом с профилем в launcher/profile-menu. В TitleBar — только если entitlement действительно workspace/project-scoped; не маркировать проект как PRO по плану отдельного пользователя.
- На текущем этапе — дизайн-макет с явной пометкой «Концепт», не бейдж около реального аккаунта. Если сервер в будущем отдаёт `active`, можно отображать PRO; при `loading/unknown/error` показывать «План не подтверждён», а не угадывать Free/PRO. Trial/expiration/cancelled выводить только при наличии соответствующих реальных полей.
- Плашка не заменяет permissions, состояние модели или статус сохранения. Tooltip сообщает подтверждённый план и доступные функции; сама декоративная плашка не обещает отсутствующие возможности.

## 7. Честные ограничения и итог приёмки

Это независимый экспертный просмотр, не пользовательское исследование и не полный QA продукта. Не проводились настоящая авторизация, оплата, запросы к LLM/MCP, изменения пользовательских файлов, Git, shell, deploy, импорт/экспорт, cloud collaboration, восстановление после crash, обновление приложения, native Windows. Не замерялись FPS, CPU, память, LCP/INP, длительные стримы и большие проекты; не запускались screen reader, настоящий мобильный браузер/IME/soft keyboard, iOS safe areas и высокие масштабы.

Сообщения об успешных полных сборках/951 тесте и прежних UI suites не перепроверялись и не служат основанием вывода «весь интерфейс готов». Исходные final-снимки — evidence конкретных состояний, не всех функций.

**Рекомендация:** сохранить визуальное направление; не объявлять универсальную keyboard/mobile-готовность до закрытия F01–F03. После них проверить валидацию/локальный путь и провести ограниченную интеграционную приёмку. Красивые новые элементы, включая PRO, не должны опережать достоверность состояния и базовые гарантии взаимодействия.
